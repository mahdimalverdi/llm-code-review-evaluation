                                                                                        Abstract
                                                  Static Application Security Testing (SAST) tools are integral to modern DevSecOps
                                              pipelines, yet tools like CodeQL, Semgrep, and SonarQube remain fundamentally constrained:
                                              they require expert-crafted queries, generate excessive false positives, and detect only prede-
                                              fined vulnerability patterns. Recent work has explored augmenting SAST with Large Lan-
                                              guage Models (LLMs), but these approaches typically use LLMs to triage existing tool outputs
                                              rather than to reason about vulnerability semantics directly.
                                                  We introduce QRS (Query, Review, Sanitize), a neuro-symbolic framework that inverts
                                              this paradigm. Rather than filtering results from static rules, QRS employs three autonomous
                                              agents that generate CodeQL queries from a structured schema definition and few-shot ex-
                                              amples, then validate findings through semantic reasoning and automated exploit synthesis.
                                              This architecture enables QRS to discover vulnerability classes beyond predefined patterns
                                              while substantially reducing false positives. We evaluate QRS on full Python packages rather
                                              than isolated snippets. In 20 historical CVEs in popular PyPI libraries, QRS achieves 90.6%
                                              detection accuracy. Applied to the 100 most-downloaded PyPI packages, QRS identified
                                              39 medium-to-high-severity vulnerabilities, 5 of which were assigned new CVEs, 5 received
                                              documentation updates, while the remaining 29 were independently discovered by concur-
                                              rent researchers, validating both the severity and discoverability of these findings. QRS
                                              accomplishes this with low time overhead and manageable token costs, demonstrating that
                                              LLM-driven query synthesis and code review can complement manually curated rule sets and
                                              uncover vulnerability patterns that evade existing industry tools.

                                         1    Introduction
                                         Static Application Security Testing (SAST) tools have become a cornerstone of modern software
                                         security practices, embedded in secure Software Development Lifecycles (SDLCs) and DevSecOps
                                         pipelines across the industry. Tools such as CodeQL [31], Semgrep/Opengrep [13, 64], Bandit [68]
                                         and SonarQube [76] enable developers to identify potential vulnerabilities before code reaches
                                         production. However, these tools suffer from fundamental limitations that undermine their ef-
                                         fectiveness in practice. For instance, traditional SAST operates by pattern-matching predefined
                                         rule sets, rendering it largely blind to the underlying application logic and semantic context. This
                                         creates a constant race between emerging vulnerability patterns and the rules designed to detect
                                         them. When rules are too narrow, complex vulnerabilities slip through undetected. On the con-
                                         trary, when rules are too broad, developers face an overwhelming volume of false positives that
                                         undermines trust in the tooling and consumes valuable engineering time to triage. Thus, fatigue
                                         from the numerous false positives may lead developers to ignore the reported issues [45]. Customiz-
                                         ing these tools to balance precision and recall requires significant expertise in query languages and
                                         deep familiarity with the target codebase, expertise that many development teams lack.


                                                                                            1
    The security of the open-source software supply chain compounds these challenges. Modern
applications depend heavily on third-party libraries, yet developers routinely trust popular pack-
ages without thorough review. This implicit trust is increasingly exploited: supply-chain attacks
have surged in recent years, with malicious or vulnerable code propagating through widely used
dependencies. The recent cases of XZ Utils [4] and Shai-Hulud worm [1] are fine examples of
open-source software compromise that led to the infection of thousands of hosts and repositories,
despite the existence of SAST tooling. Thus, while SAST tools can scan dependencies, their
rigid rule-based approach struggles to identify novel vulnerability patterns or context-dependent
security issues in unfamiliar codebases.
    Large Language Models (LLMs) offer a potential remedy through their capacity for semantic
understanding and contextual reasoning. Recent work has explored the application of LLMs
to vulnerability detection, taking advantage of their ability to comprehend code logic beyond
surface-level patterns [46, 78, 41, 22]. However, LLMs are fundamentally prediction-based systems,
sophisticated pattern matchers that lack mechanisms for self-verification. Without being grounded
in external tools or structured workflows, they hallucinate vulnerabilities, miss critical context,
and produce inconsistent results. Directly prompting an LLM to review code yields unreliable
findings that still require extensive human validation. Moreover, they heavily rely on training
datasets [41] and tend to degrade when evaluated on large codebases.
    In this work, we introduce QRS (Query, Review, Sanitize), a hybrid framework that combines
the precision of SAST with the semantic reasoning capabilities of LLMs through a pipeline of three
autonomous agents. Rather than replacing traditional tools or relying solely on LLM inference,
QRS orchestrates both in an iterative, mutually reinforcing workflow pipeline. Unlike prior works
like LLMxCPG [46] and QLPro [43], which require expensive fine-tuning, QRS demonstrates that
generic LLMs can synthesize complex CodeQL logic using a lightweight schema definition. The
framework generates vulnerability-detection queries from a structured schema definition and few-
shot examples, eliminating the need for manually maintained rule sets while preserving the rigor
of static analysis and strengthening the final output through evidence-based reasoning. In this
regard, the QRS framework decouples the vulnerability detection process into three specialized
agents, each augmented with custom toolsets:
   • The Query (Q) agent synthesizes CodeQL queries from self-imposed hypotheses, after
     being injected with a concise knowledge schema, translating high-level vulnerability descrip-
     tions into precise static analysis rules without requiring manual query authorship.
   • The Review (R) agent performs a semantic reachability verification, analyzing the code
     context surrounding each potential finding, tracing data flows from source to sink, thoroughly
     assessing exploitability, and generating exploitation suggestions before submitting validated
     findings.
   • The Sanitize (S) agent performs a final context-free and evidence-only assessment in
     a clean environment, pruning false positives and consolidating results to produce high-
     confidence vulnerability reports, while assigning labels to each finding.
This architecture effectively mimics the workflow of an expert code auditor while maintaining low
context windows, a bounded runtime, and manageable token costs, which are critical for practical
deployment at scale.
   To assess the efficacy of QRS, we evaluate our framework in two complementary settings. First,
we evaluated the detection accuracy on 20 historical vulnerabilities in popular PyPI libraries using
precompiled high-level strategy instructions, demonstrating that QRS reliably identifies known
vulnerability patterns. Second, we apply QRS to the 100 most popular PyPI packages as of
November 2025, simulating real-world discovery conditions in heavily monitored source code.
Main contributions. We introduce QRS, a highly configurable and extendable multi-agent
framework that demonstrates practical security applications beyond benchmark performance. Our
evaluation against the 100 most popular PyPI packages identified 34 CVEs, 5 of which we timely
responsibly disclosed and received a CVE (CVSS range 4.5–8.6), and 5 additional issues that were
acknowledged by the maintainer updates on documentation. The newly discovered CVEs affected
packages that surpass 1.8 billion monthly downloads, are maintained by over 800 contributors,


                                                 2
and are dependencies of more than 2 million repositories. The vulnerabilities persisted despite
being scanned by GitHub’s automated toolchain of CodeQL, Dependabot, and AI-enabled Copilot
Autofix, and were patched within less than a month, and in most cases, within a few days. The
findings include complex vulnerability classes, such as TOCTOU Race Conditions, ASN.1 octet
memory exhaustion, and Path Traversal chains, demonstrating the framework’s ability to detect
exotic patterns that evade traditional static code analysis and security expert reviews. Contrary
to the current state of the art, QRS uses LLMs to craft CodeQL queries and, using agentic
loops, prunes noise, labels the results, prioritizes them, and explores their exploitability. Thus, we
demonstrate that LLM architectures can assist in discovering complex real-world security issues
at scale, including cases missed by existing automated tools.

2     The QRS Methodology
2.1    Scope
QRS targets a practical threat scenario end-to-end, identifying exploitable vulnerabilities in source
code before attackers discover and weaponize them in production. Thus, we assume defenders have
access to the source code and seek to minimize manual review effort while maximizing detection
of genuine security issues. Moreover, we assume defenders have access to LLMs that they use
to craft their CodeQL queries. Note that all CodeQL queries are executed locally, and LLMs
parse only the specific tool output, not the entire codebase. Therefore, the codebase is not
fully exposed to an LLM. Moreover, we do not evaluate adversarial code intentionally crafted
to evade LLM-guided query synthesis, which remains an important direction for future work.
As such, our experimental setup does not address: (i) vulnerabilities in compiled extensions or
native code, (ii) logic vulnerabilities requiring dynamic analysis, (iii) supply-chain attacks at
the package distribution level (e.g., compromised PyPI uploads), and (iv) adversarial evasion
where attackers specifically craft code to bypass QRS detection. Finally, since there are tools
to efficiently determine whether a specific library is known to be vulnerable, we do not consider
imported libraries whose code is not provided in the package.
    These exclusions reflect practical scoping decisions rather than fundamental limitations. Com-
piled extensions and native code require binary analysis techniques outside CodeQL’s source-level
approach. Logic vulnerabilities that necessitate dynamic analysis constitute a complementary
threat class that is better addressed by fuzzing or runtime testing. Distribution-level supply-chain
attacks (e.g., compromised PyPI uploads) occur outside the source code and require monitor-
ing of package repositories rather than code analysis. Finally, while adversarial evasion remains
theoretically possible, our evaluation against heavily-scrutinized production packages suggests
that current obfuscation techniques in legitimate codebases do not significantly impede detection.
These boundaries align with standard SAST threat models and do not diminish QRS’s utility for
its intended use case: identifying exploitable vulnerabilities in source code prior to deployment.

2.2    Overview
QRS is a modular, configurable, rule-synthesizing, neuro-symbolic triad of autonomous agents
that collaborate to detect and validate security vulnerabilities. The framework is model-agnostic;
it unifies model APIs via LiteLLM [49], providing compatibility with Gemini, Claude, GPT, and
DeepSeek (both Chat and Reasoner variants). The architecture balances contextual understanding
with computational efficiency through a hybrid approach combining custom-built tooling with
LLM-based reasoning and AI agents.



                                                  3
    The architectural separation of agents renders QRS inherently model and language-agnostic.
Since CodeQL provides unified relational representations (ASTs, CFGs, DFGs) [28] for languages
such as C/C++, Java, Go, and JavaScript [33], QRS can handle any supported language. By
swapping the target language’s QL knowledge predicates, it can scale across diverse technology
stacks without requiring fundamental architectural re-engineering. Our experimental setup in
section 3 focuses on Python packages and a set of distinct configurations; nonetheless, it can
be easily ported to support other programming languages. To extend functionality, an update
on knowledge and system prompts is sufficient to switch to any CodeQL-supported analysis.
Additionally, QRS can be configured to run with a set of attributes per agent, including model,
temperature, iterations, maximum output tokens, and other generic caching attributes, according
to the user’s needs.

    Figure 1 illustrates the framework’s architecture. The three core components are: the Q agent
(hypothesis and query generation and refinement engine), which synthesizes CodeQL queries from
minimal documentation; the R agent (review, exploitation suggestion and reasoning engine),
which performs semantic verification of potential findings by analyzing sources, sinks and code
flows with reasoning; and the S agent arbitration and finding sanitization engine), which renders
final verdicts, filters false positives and assigns multiple labels to findings. Each agent operates
with a dedicated toolset and iterates up to a user-defined limit. Custom static preprocessing
utilities execute before each agent to prepare inputs, and all output reports undergo manual
expert review for final acceptance or rejection of the findings.
    Each scan can be configured to involve any combination of models, iterations, maximum tokens,
and temperature variations. For the sake of brevity, the model combinations stayed within the
same family, a ‘big’ model to craft queries and ‘smaller’ ones to review code or produce Proof-of-
Concept (PoC) exploitation snippets, e.g., GPT-5.1 for Q, and GPT-4.1 for R and S, except for
DeepSeek, which provides only Chat and Reasoner models. The same configuration on maximum
iterations, output tokens, and temperatures of 0 and 1 has been tested. We evaluate temperature
settings of 0 and 1 because temperature behavior varies across model families, and these values
represent reasonable bounds for code generation and review tasks with negligible hallucinations.
    All agents have a structured markdown input in their system_prompt with a declarative Role
- who the agent is, Goal - what is its purpose, Tools - what are its new skills, Strategy - how to
tackle tasks, and Examples when necessary. Each agent has an additional section of instructions
specific to the task.

2.3     Query Generation
The Q agent serves as the framework’s primary reasoning engine, generating high-level security
hypotheses into executable CodeQL logic. Unlike traditional SAST, Q operates as a generative
synthesis engine that dynamically constructs and refines queries tailored to the library’s context.
Besides hypotheses, the agent focuses on the severity levels provided and assigns a CWE to


                                                                             4
each hypothesis. The main workflow is governed by the following modules: Structural Library
Reconnaissance, Retrieval-Augmented QL Schema Learning, and Iterative Syntax Refinement with
self-healing capabilities.
Structural Library Reconnaissance. To address the ‘cold-start’ problem, inherent in zero rule
knowledge analysis, the Q agent can run the get_package_profile utility. This custom utility
captures file paths, line numbers, import dependencies, and package metadata. The agent runs
this tool only once during initialization; the tool performs a lightweight static scan and generates
a JSON artifact of the scanned library, see Listing 6 in the Appendix.
Retrieval-Augmented Schema. The operation without pre-defined query rules requires a criti-
cal component of our framework. The Q agent is initialized with a compact context knowledge.md
file, which serves as a sparse schema definition. The file contains CodeQL syntax primitives and
canonical patterns, see Listing 7 in the Appendix.
Iterative Refinement. CodeQL’s declarative syntax is strict, often leading to compilation fail-
ures in LLM-generated code. When a generated query fails to execute, the agent enters a recovery
fixup_query subroutine (see Listing 1 in Appendix) for: (i) Isolation: The failed raw query
and compilation errors (stderr) are moved to a dedicated, ephemeral context thread, preventing
‘context pollution’ and ensuring focus on the same hypothesis, severity, and CWE targets. (ii) Re-
finement: The agent attempts to patch the failed query’s logic based on each error in an iterative
manner. (iii) Constraint: This separate agentic loop is bounded by a retry budget (default: 3
attempts). If the query still fails after budget exhaustion, the results are returned to the main
thread, forcing the agent to either change approach or discard this hypothesis.
     Successfully compiled queries, as shown in Listing 4 in the Appendix, are executed locally
against the CodeQL database and are sent back to the Q agent to correlate the output with
the original hypothesis to refine it accordingly. These structured findings are then served as
a navigational map for the downstream R agent using the create_report tool in JSON/Sarif
format.

2.3.1   Natural Language Steering Strategy
To accommodate targeted audit requirements or specific bug-hunting scenarios, the Q agent im-
plements a Natural Language Steering interface configuration. This mechanism allows researchers
to inject an additional high-level directive via a preprompt.md file, see Listing 9 in the Appendix,
and instruct the agent to focus on specific types of vulnerabilities (e.g., CWEs), severities, or even
set restrictions and adjust the weights of each scan. This way, the framework can be extended
into a broader-spectrum scanner that bridges the gap between human intuition and automated
analysis.

2.4     Semantic Review & Exploitation
While Q agent can identify vulnerability patterns based on structural logic, it lacks semantic
depth to determine exploitability, whether a code snippet can actually be exploited. The R
agent is a semantic verification and evidence-gathering engine that acts as an investigator before
solving a crime. It is a cognitive workflow, with a report of potential findings in hand, trying to
identify points of interest in the codebase. The main workflow here is based on four components:
MITRE Taxonomy-Driven Clustering, Iterative Context Reconstruction, Evidence-Based judgment
& Reasoning, and Exploitation. The output of these tasks is handed over in JSON/Sarif format
to the downstream Sanitization (S) agent after all verdict submissions have been completed.
MITRE Taxonomy-Driven Clustering. Raw results without semantics can often lead to
context window degradation or the omission of more complex scenarios. As coding patterns
and anti-patterns tend to recur, findings are clustered by relevance according to MITRE’s CWE
database hierarchy [50]. By pivoting from file locations into groups of findings, we change R’s
viewpoint to a taxonomy-driven review, based on: severity, prevalence, likelihood, CWE ID, and
related CWE IDs. Each group is also minified to remove duplicates in file locations, code flows,
and unnecessary fields. Each cluster is then processed in an isolated context thread, with its
own iteration budget set to 10 × Nf indings , ensuring thread context separation. This may lead to
duplicate entries, since the same finding may appear multiple times in Q queries and be mutated


                                                  5
in various cluster definitions. An extra ‘pattern-stuttering’ elimination mechanism on duplicate
findings with slight variations exists post-R run.
Iterative Context Reconstruction. Unlike a traditional SAST tool that alerts a developer
with static snapshots of findings, the R agent iteratively interrogates the codebase to reason and
validate. Two semantic-slicing tools are used for this purpose. First, trace_flow maps the flow
of a propagation path from the source to the sink with a line tolerance limit of 1 to 3 surrounding
lines. Beneath this tool is a single parameterized, hard-coded CodeQL predicate query with
sink-to-source and tolerance parameters. Then, grep_search is a sandboxed local grep search
capability. It enables the agent to perform a pattern-enabled grep under a restricted local path.
Bounded raw code snippet extraction is also available and is usually the most preferred tool of
tested AI models, as we will see later on subsection 3.5.
Evidence & Reasoning judgment. To enhance the traditional binary true-positive/false-
positive verdict system, we introduce a more nuanced evidence-based classification. The R agent
is required to provide classic SAST fields, i.e., file_path:start_line, alongside reasoning, code
context, and data flow analysis, forcing the agent to prove the verdict claim as a: (i) True Positive
(TP) (Confidence ≥ 90%): A vulnerable code pattern finding, with a high degree of confidence.
Requires generating a minimal exploit snippet, a scenario, the prerequisites to enable the attack,
the likelihood, the impact, and the exploitability level. (ii) Manual Review (MR) (Confidence
≥ 70%): Similar to a TP, but the complexity of the exploit chain or the agent’s decision horizon
deems it unable to reach a certainty. (iii) False Positive (FP): A non-vulnerable code pattern. By
forcing the model to generate the above, we leverage the chain-of-thought effect [6, 37, 63, 21],
allowing the agent to articulate a plausible exploitation path.
Exploitation Synthesis. To bridge the gap between theoretical reachability and practical ex-
ploitability, the R agent must strongly verify practical exploitability. Once a vulnerability candi-
date is semantically verified and ready to be submitted as a finding, the agent plays an additional
adversarial role and must synthesize a minimal Proof-of-Concept (PoC) working exploit. This in-
volves constraint solving; the prerequisites to materialize the attack scenario, artifact construction;
the payload, and a semantic verification, a scenario for the attack, including the scenario’s cat-
egory (e.g., Remote code execution), likelihood (low-high), impact (low-high), and exploitability
(low-high), see Listing 2 and Listing 3 in the Appendix.

2.4.1   Natural Language Steering Strategy
Similarly to Q, the R agent implements a natural language steering interface capability, allowing
the injection of an extra high-level directive via a preprompt.md strategy, see Listing 5 in the
Appendix, and steers the agent to look for specific types of vulnerabilities, CWEs, TP or FP
indicators, and critical focus areas, adjusting weights of each review process.

2.5     Sanitization & Verdict
The final component of the neuro-symbolic triad is the S agent. The agent is designed to function
as an independent judge of the holistic picture. While Q and R collaborate hand-in-hand in
context, to avoid potential cascading of hallucinations, the S agent is a ‘clean slate’ and adds a
final verdict on what the other two ‘reported’. Compared to the other two agents that run their
tools according to their preferences, the S agent populates context in a series.
    Agent S is modular, minimal, and detachable from the workflow. Yet, the agent reduces noise
as a context-free review protocol and assigns taxonomies on each finding, while strengthening or
weakening R’s decisions, and adding insights for expert analysts on each finding being examined
through three verification layers: Novelty Verification, Operational Analysis, and Vulnerability
Classification.
Novelty Verification. To distinguish between known technical debt and genuine zero-day
threats, the agent integrates a retrieval tool that directly queries the Common Vulnerabilities
and Exposures (CVE) database [57] to determine whether the issue is a repetition of a published
CVE or a novel finding. To avoid direct CVE correlation with the finding being examined, the
agent calls search_cve after the review phase has completed, just to assign a label.



                                                  6
Operational Analysis. Frequent sources of false positives in static analysis are: the absence of
context, API reachability (e.g., the vulnerability is in deprecated or internal-only code), and non-
production code (e.g., the vulnerability is in a test suite for the actual library). The agent analyzes
the surrounding logic, code flows, and file paths, respectively, to determine the operational scope
of each finding before reaching a verdict.
Vulnerability Classification. Before finalizing, the agent applies a multi-label tagging tax-
onomy to move further away from the binary true/false positive result, and adds actionable in-
telligence concerns. The available flags are (i) KNOWN_CVE: already published CVE, matching the
finding; (ii) ZERO_DAY: a finding with no matching CVE, high to critical severity, and relatively easy
to exploit; (iii) NOVEL_FINDING: a finding with no matching CVE, medium to high severity, and
exploitability uncertainty; (iv) BUILD_SCRIPT | TEST_CODE: a finding found in a build script or a
test/example/smoke code; (v) EXPLOITABILITY: a vulnerability with exploitability and prerequi-
site concerns in context; (vi) HALLUCINATION: the claimed code context does not match the finding;
(vii) CODE_SMELL: not a vulnerability but a best-practice issue, and (viii) CONTEXT_MISMATCH: the
finding does not align with the package. Upon completion, each finalized verdict as seen in List-
ing 8 is appended to R’s respective artifact as seen in Listing 2, presenting an enhanced and
curated JSON/Sarif output to the expert security analyst.


3     Framework validation
According to the TIOBE index [79], Python is the most popular language. Moreover, there is the
Python Package Index (PyPI), a centralized repository of open-source Python packages. Thus,
using PyPI as a reference point, we can establish a ground-truth dataset in a real-world setting and
maximize the potential impact of the research. As such, we evaluate QRS on two datasets: first,
the Historical 20 (Hist20) dataset to establish the framework’s detection accuracy, and second, a
real-world production dataset on the Top 100 (Top100) PyPI packages.
Framework configuration. Since QRS can run with any model combination, we use higher-
reasoning models for Q agent and lower for R and S, to limit token consumption on less intensive
tasks. To avoid cross-model contamination, we keep each configuration within the same model
family and assign temperature values of 0 and 1, corresponding to deterministic and creative sam-
pling, respectively. We annotate models in short with their respective temperature configuration
subscripts as explained in Table 1.

3.1    Dataset Construction
To collect these two datasets, we used the official Python Index Project [23] and a snapshot of the
most downloaded PyPI packages from the Open-Source project ‘Top PyPI Packages’ [34], as of
November 2025. We implemented an automated crawler to retrieve archived source distributions
from PyPI’s repository for direct analysis. No further processing was performed, since QRS accepts
archived packages and handles extraction and CodeQL database generation.

3.2    Metrics Definitions
Vulnerability detection in our datasets lacks the binary labels of curated lab benchmarks. We
establish ground truth through a multi-stage process and define metrics through expert review
as (i) True Positive (TP)/Manual Review (MR): The finding describes a genuine or al-
most certain vulnerability. Findings with too many prerequisites are considered TP, since the
code snippet is vulnerable, but includes exploitability concerns, in agreement with expert review.
(ii) False Positive (FP): The finding describes a non-vulnerable code snippet. Either the at-
tack vector is non-feasible or mitigated by the runtime context. (iii) True Negative (TN): The
finding describes a non-vulnerable code snippet, in agreement with expert review, and (iv) False
Negative (FN): The finding describes a missed vulnerability. To calculate metrics, we use the
confusion matrix of Table 2. Note that our metric definition makes them objective and rigorous.
For example, we do not simply declare a new vulnerability and mark it as positive; it is verified
by the package owners and through CVE publication. Thus, although the ground-truth labeling
is more limited, especially for Top100, the results remain subject to expert judgment and main-
tainer feedback, introducing unavoidable subjectivity despite our efforts to standardize validation.
However, this approach does not inflate our results.

3.3    Historical 20 Dataset
To establish baselines, we curate a dataset of 20 PyPI package versions with reported CVEs,
containing 20 CVEs spanning 2018–2025 across 12 CWE categories (see Table 3). Each package
contains at least one CVE with a published advisory right before patch application. We aim to
cover a diverse set of vulnerability classes spanning from Code Execution, Cross-Site Scripting
(XSS), or Denial-of-Service (Re/DoS), to more contextualized classes that require understanding
of HTTP Request Smuggling, Sensitive Information Disclosure between 30x redirects on protocol
downgrades (from HTTPS to HTTP), or incomplete validations on cookie header parsing and file
uploads. Of course, due to the limited sample size (N=20), metrics on the Hist20 dataset should
be interpreted with caution.
Consensus. To assess functionality and efficacy, QRS ran with 4 basic configurations (C0 , G0 ,
GPT0 , DR0 ), included natural language instructions, and focused only on a subset of CWEs, with
the CVE search tool disabled to avoid direct correlation. QRS detected 19/20 CVEs across Hist20
packages in Table 3, with an average configuration consensus of 2.7/4. This means that at least 3
configurations are required to guarantee catching 95% of the CVEs (G0 achieved 16/20), as seen
in Table 4, while achieving a high prediction performance output (see Table 5).

4     Empirical Observations
4.1    Failed CVE-2021-32677 detection
CVE-2021-32677 (FastAPI open redirect) was not detected by any model configuration. Manual
inspection revealed that the vulnerability requires reasoning about HTTP redirect semantics and
framework-specific routing behavior, patterns not captured by our current QL knowledge base.
More precisely, the vulnerability stems from the fact that requests with content type text/plain
are exempt from CORS preflights. The latter does not match any specific code pattern. However,
extending the knowledge schema of QRS with web framework routing primitives could potentially
identify further vulnerabilities.

4.2    Comparison against SAST tools
To demonstrate the advantages over purely syntactic pattern matching, we benchmark QRS
against 3 widely-known open-source tools, namely Opengrep-v.1.15.1 [64], an open-source fork of
Semgrep, using the standard community Python Semgrep ruleset [74], Bandit-v1.9.3 [68], a more
sophisticated AST-based Python scanner, and CodeQL-v2.23.0 using the library’s ruleset [26].
    The former two tools exhibited severe alert fatigue on the Top100 dataset. More precisely,
Opengrep generated 1251 warnings, Bandit generated 653 medium-to-high-severity alerts (more
than 48k if low-severity alerts are included), and CodeQL generated 136. Compared with our nois-
iest configuration (i.e., C0 ), which produced 140 TP candidate findings, we demonstrate a superior
signal-to-noise ratio than the two tools and include more meaningful findings than CodeQL.
    More precisely, using all 39 vulnerabilities on Table 11 as ground truth, Opengrep and Cod-
eQL failed to detect any novel CVE, whereas Bandit pinpointed a potential Path Traversal in
setuptools, with no clear indication of how tarfile.extractall was actually vulnerable. Open-
grep and Bandit primarily detected vulnerabilities involving direct use of dangerous functions (e.g.,
eval and pickle.load) that match simple syntactic patterns, yet without any context. CodeQL,
with its standard Python security query suite [29], was unable to find any of the related issues. The
reader may refer to Table 12 for detection metrics. However, beyond simple syntactic patterns,
QRS detected vulnerabilities requiring data flow analysis or cross-module reasoning.

4.3     Comparison against LLM-based Research
Although metrics are not directly comparable due to the vast differences in datasets; a common

   Notably, while overall classification accuracy and recall exceed prior work, precision is lower,
indicating a higher FP rate in real-world scenarios; the best precision configuration (DC0 ) achieves

4.4       Model-specific observations
DeepSeek-Reasoner exhibited the highest prediction rates in the Hist20 dataset setup, despite be-
ing the slowest model at ≈ 22 minutes, and operated for a fraction of a cent. However, it displayed
very conservative approaches to tool-calling and the lowest prediction rates on the Top100 dataset,
indicating that guided strategies may be catalytic for the model. Its cost effectiveness was remark-
able at $0.08 per scan, making it approximately 18 times cheaper than Claude. DeepSeek-Chat
proved inefficient in utilizing toolsets, often falling into no-operation iterations, resulting in only
≈ 1 finding submissions per scan or findings of lesser quality.
    Gemini seems to be positioned as the middle-ground option between speed, cost, and thor-
oughness. The models displayed a balanced approach, executing ≈ 14 queries and extracting ≈ 5
code snippets per scan, with a processing time of ≈ 11 mins, while maintaining highly competitive
precision metrics and catching the most CVEs in the Hist20 dataset. Notably, Gemini preferred
to avoid fixing query compilation failures, calling the query-fix subroutine at most once per scan.


                                                      16
    GPT completions were the fastest (≈ 8 min. per scan) but achieved among the lowest pre-
diction rates, on par with DeepSeek models; the chat model often underperformed due to no-ops.
GPT models showed a tendency toward premature completion and had the highest query gen-
eration failure rates and query-fix subroutine visits, indicating challenges with CodeQL syntax.
Consequently, the models submitted fewer findings.
    Claude was the most efficient and complete model for query generation and code review, with
runtimes of ≈ 11 mins, achieving the highest accuracy and precision rates in a real-world setting
while uncovering all complex vulnerabilities, still being the priciest at $1.4 per scan. Claude did
not perform that well in the Hist20 dataset, only catching 12/20, but was able to discover all
CVE-assigned vulnerabilities in the Top100 dataset. Moreover, temperature variations between 0
and 1 in the Top100 dataset revealed subtle differences. Zero-temperature configurations generally
produced more consistent results, whereas temperature 1.0 occasionally identified vulnerabilities
missed by deterministic runs, as evidenced by CVE-2026-22702 being detected only by C1 . Thus,
running multiple temperature configurations provides complementary coverage rather than redun-
dant scanning.
    The consensus analysis revealed that reliable vulnerability detection required multiple, diverse
model configurations. In both datasets, a minimum of 3 configurations is recommended, indicating
that broader model coverage compensates for the absence of targeted instructions. Finally, from a
cost-effectiveness perspective, at an overall cost of $5.3 per 10-configuration package scans, QRS
provides a substantial cost reduction compared to traditional security audits while maintaining
the capability to discover CVE-worthy vulnerabilities in production libraries.


5    Discussion & Limitations
Based on the nature of packages, the CWE focus shifted for each package profile, and QRS success-
fully generated hypotheses and findings across 115 unique CWEs, focusing mainly on: Injection
& Code Execution, Path Traversal, File System Access, Denial-of-Service, Cryptographic Weak-
nesses, and Race Conditions. Different packages may exhibit different vulnerability distributions.
The reader may refer to the Appendix Figure 6 for more details about CWEs
    Determinism in LLMs is a complex topic, as multiple runs within the same model family may
yield different results; however, they tend to converge to similar outcomes and achieve better
predictive performance metrics when given high-level instructions or a specific CWE focus.
    Model families exhibit distinct characteristics and behaviors; for example, GPT may appear less
capable of crafting queries without examples or documentation and may prematurely terminate
even when instructed otherwise, whereas DeepSeek-reasoner requires natural language navigation
to perform optimally. A diverse model set increases coverage and quality output.
    Traditional manual security audits cost thousands of dollars, whereas the QRS, even with
multiple models, configurations, and scans, can remain in the single digits and deliver significant
Return on Investment (ROI) with reasonable scan durations. No fine-tuning or pre-training ap-
proaches were also performed, as we used the models as-they-are and compiled a compact file to
augment their knowledge, and created a custom toolset to dictate their capabilities.
    QRS handled large libraries without substantially increasing token consumption, which in
other cases could lead to context derailing and LLM hallucinations. The depth of results on
highly maintained libraries that affect millions of repositories, and the output complexity, are also
intriguing outcomes, demonstrating that LLMs can identify and combine patterns that humans
or other static tools may miss. QRS can also perform parallel and multi-provider scanning tasks,
enabling high scalability in containerized environments, as it is a pure Python framework with
standard pip dependencies.
    Our framework was limited to only scanning Python packages during this setup. Allowing
QRS to operate on multi-language code is relatively easy to tackle, since it only requires (i) the
language-of-interest to be supported by CodeQL, (ii) an extra automated database creation for
the specific language, and (iii) multi-language prompt instructions.

6     Background and Related Work
To contextualize the QRS framework, we review prior work in static analysis, CodeQL-based
program analysis, and recent advances in agentic AI for cybersecurity.
Static Analysis & Taint Tracking. SAST examines source code to detect potential vulnerabil-
ities without execution. Taint analysis, a core SAST technique, tracks data flows from untrusted
sources to sensitive sinks and has been widely used to identify issues such as injection vulnerabili-
ties and insecure data handling [73]. Despite its effectiveness, static taint analysis often struggles
with scalability and precision when applied to large or dynamically-typed codebases, frequently
leading to false positives or negatives [72].
CodeQL & Code Analysis. CodeQL [31], developed by GitHub to automate code security
scanning, represents a state-of-the-art tool in semantic code analysis. It supports most major pro-
gramming languages and can be configured to automatically scan all public GitHub repositories.
Hence, it can significantly enhance the security of open-source software. Unlike rule-based pat-
tern matchers, CodeQL converts code into abstract, high-level objects and control flows, stripping
out non-semantics, and storing the results in a relational database. Researchers can query the
database using QL [25] in an SQL-like manner to detect sources, sinks, and flow configurations.
While powerful, CodeQL has a steep learning curve, making it difficult to write effective queries
without deep expertise in QL’s syntax and the target library’s API.
Agentic AI. LLMs have demonstrated remarkable capabilities in contextualizing code, yet suffer
from ‘hallucinations’, generating potentially plausible but incorrect facts. AI agents extend LLMs
when equipped with tools and reasoning iterations. With tools, LLMs can execute functions that
allow the model to interact with the environment or retrieve knowledge not directly available [8],
e.g., retrieve online content, perform system commands, and ingest their output. On the other
hand, reasoning iterations can be considered chain-of-thought operations that enable running
agents to plan, execute, and observe outputs to refine their next actions [6, 5].
    Nevertheless, one of the big advantages of LLMs is their unpredictability. Temperature con-
figurations affect how deterministic or creative agents can be. For code generation or code review
tasks, values between 0 and 1 are usually recommended [19, 38, 7, 60].

6.1    LLMs in Vulnerability Analysis
The intersection of LLMs and static analysis for vulnerability detection has emerged as a rapidly
evolving research area. The landscape of LLM-assisted vulnerability detection, at the moment of
writing, can be divided into three main categories, each with distinct trade-offs between automa-
tion, contextual reasoning, and practical applicability.
Pattern-Based Classifiers. Discriminative approaches such as VulBERTa [42], VulSim [75],
and ReGVD [51] employ transformer architectures or contrastive learning to classify code. While
achieving reasonable accuracy on curated benchmarks, these methods require extensive labeled
training data and struggle with novel vulnerability patterns not seen during training, limiting
their effectiveness on real-world codebases.
LLM-Guided Static Analysis. Other hybrid approaches such as LLMxCPG [46] and GPTScan [78]
combine Code Property Graphs (CPG) with LLM reasoning to identify vulnerability-relevant code
slices. However, these frameworks operate in a single-pass manner, without iterative refinement
or recovery from initial misclassifications, slicing, or querying failures.
Multi-Agent Agentic Frameworks. Recent work explores multi-agent architectures for vul-
nerability detection. LLM4Vuln [77] demonstrates that external knowledge enhancement benefits
logic-heavy vulnerabilities but may harm detection in traditional languages. VulAgent [82] in-
troduces hypothesis validation with specialized agents for multi-view detection, achieving 26.6%
pair-wise correct prediction on PrimeVul. Notably, they report reducing FP rates by 36% through
structured hypothesis pruning.
    IRIS [48] is a taint specification engine that leverages LLMs for the specifications and augments
CodeQL. However, IRIS requires explicit CWE specification as input and relies on CodeQL’s call
graph to connect sources and sinks. MoCQ [47] is a neuro-symbolic framework that generates
vulnerability patterns via LLMs to extract patterns and translate them into detection queries for



                                                 18
tools. While MoCQ focuses on pattern generalization, QRS emphasizes per-package deep analysis
with iterative hypothesis refinements, enabling the detection of package-specific vulnerabilities.
    LARA [83] is a static taint analysis framework for embedded systems that leverages semantic
relations between frontend inputs (URIs and keys) and backend handling code, and combines
pattern-based static analysis with LLM-aided semantic reasoning. In particular, LLMs are used
to analyze decompiled backend code and infer the semantic roles of functions, such as identifying
URI registration functions and key-handling routines, by capturing intent that is difficult to express
through syntactic patterns alone. By intersecting LLM-derived results with rule-based analysis,
LARA reduces false positives while retaining high coverage, enabling accurate identification of both
hidden and non-hidden taint sources. Evaluated on real-world IoT firmware, LARA discovered
245 previously unknown vulnerabilities that were confirmed by vendors, with 162 assigned CVE
identifiers.
    For automated Query synthesis, QLCoder [81] is an agentic framework that generates CodeQL
queries directly from CVE metadata, built upon Claude, and provides a custom MCP (Model
Context Protocol) interface for syntactic guidance. The key distinction is that QLCoder requires
CVE metadata inputs and focuses on reproducing known vulnerabilities. QLPro [43] presents
a framework for automated CodeQL rule generation for individual projects, employing LLMs
with a triple-voting mechanism for classification. While QLPro excels at systematic API extrac-
tion and classification for Java projects, QRS takes a broader approach by generating complete
logic, including inter-procedural data flows, without requiring API-level enumeration, and extends
beyond Java. For post-scan filtering, LLM-SAST Genius [2] examines the synergy between tradi-
tional SAST and LLMs to triage alerts and reduce noise. QRS inverts this paradigm by positioning
LLM-driven agents at every stage of the pipeline. This end-to-end integration enables our frame-
work to go beyond FP filtering and actively discover real-world, exploitable vulnerabilities that
any rule-based scanner would miss entirely.
    Finally, we report CVE-Genie [80] addresses the complementary problem of automatically re-
producing known vulnerabilities through their CVE format to generate a high-quality vulnerability
datasets using a multi-agent framework.


7    Conclusion & Future Work
This work introduces QRS, a neuro-symbolic framework that inverts the dominant paradigm for
LLM-assisted vulnerability detection. Most prior work applies language models as post hoc filters
to rule-based scanner outputs. QRS employs LLMs as the generative core to synthesize CodeQL
queries from a minimal schema, perform semantic validation through iterative code inspection,
and produce PoC exploits, without predefined rules, package knowledge, fine-tuning, or training
data beyond a few-shot examples.
    Our evaluation yields three main findings. First, QRS achieves high accuracy and recall on
vulnerabilities: a combined configuration set detected 19/20 historical CVEs in our Hist20 dataset,
and reached 90.62% accuracy, 86.96% precision, and 100.00% recall. Second, QRS discovers
novel and complex vulnerabilities in production code that existing tooling misses. Scanning the
100 most-downloaded PyPI packages, which are already being monitored by GitHub’s Advanced
Security with CodeQL, Dependabot, and AI Copilot, QRS identified 39 vulnerabilities, 5 of which
were previously unknown that received CVEs, and 5 maintainer-acknowledged issues. Third,
QRS substantially reduces alert fatigue. Our noisiest configuration achieved a 65% reduction and
93.84% classification accuracy. Opengrep and Bandit on the same corpus produced more than
an order of magnitude alerts, whereas CodeQL yielded no relevant findings. Still, the framework
operates at a rather low cost across all model families, making comparisons favorable to manual
security audits while preserving the interpretability that automated approaches typically sacrifice.
Moreover, every finding includes query provenance, data-flow evidence, and PoC exploit code. Our
experiments also showed that model-specific behaviors affect coverage, e.g., GPT configurations
exhibited premature termination, whereas DeepSeek underutilized available tooling. Finally, our
ground truth for the Top100 dataset relies on expert review rather than an exhaustive manual
audit, potentially underestimating both TP and FP rates.
    The architectural separation of QRS agents seamlessly extends to cross-language analysis.


                                                 19
CodeQL’s unified representations for C/C++, Java, and Go require only schema adaptation,
not a fundamental redesign; thus, they will be implemented in the future. More sophisticated
clustering that spans CWE boundaries may reveal multi-stage vulnerabilities that are invisible
to taxonomy-driven grouping. We believe that replacing the sequential pipeline with continuous
inter-agent feedback could reduce verdict inconsistencies; therefore, we will explore this approach in
future work. Finally, we plan to integrate lightweight dynamic validation by executing generated
exploits in sandboxed environments to provide stronger evidence of exploitability than static
reasoning alone.
